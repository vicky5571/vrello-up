### CRITICAL PROJECT FINDING: `prisma migrate dev` is unusable in this repo

`prisma/migrations/` contains a single **abandoned early snapshot** — `20260906221636_marcom_port/migration.sql` creates only **10 of the 17 tables** and **2 of the 41 indexes**. The other 7 tables and 39 indexes were added via `prisma db push` and never captured. Consequences:

- `prisma migrate dev` detects permanent drift and demands a **full database reset** (all data lost). It aborted rather than resetting (non-interactive).
- `prisma migrate status` reports "up to date" regardless — it only checks `_prisma_migrations` for pending entries, not schema equality. **Do not trust it.**
- The correct mechanism is **`prisma db push`**, preceded by `prisma migrate diff --from-url $DATABASE_URL --to-schema-datamodel prisma/schema.prisma --script` to inspect the pending delta.
- `db push` refuses to run when it detects a data-loss warning; `--accept-data-loss` is required **only** in that case, and only after verifying the warning's condition does not hold.
- **Deployment caveat:** because these changes were pushed, they record nothing in `prisma/migrations/` and are **not reproducible via `prisma migrate deploy`**. A CI/CD pipeline using `migrate deploy` will silently keep the old schema. The deploy contract needs an explicit decision.

Backup taken before any schema work: `~/vrelloup-backups/vrelloup-20260927-203537.sql`.

### Reusable finding: `@ts-expect-error` + multi-line imports is a trap
This repo imports test modules with explicit `.ts` extensions because Node's strip-types runner needs them, and suppresses the resulting TS5097 with a `// @ts-expect-error` directly above. **The directive only covers errors on the immediately following line.** Reformatting such an import to multi-line moves TS5097/TS2305 onto the *specifier* lines and orphans the directive → `TS2578 Unused '@ts-expect-error' directive`. Keep these imports on ONE line (repo-wide convention: `automationRules.test.ts:3-4`, `workspaceSwitch.test.ts:4-5`, etc.).

Corollary: because that directive suppresses *every* error on the import line, a missing named export from such a module is silently masked — tsc stays green. Never treat a clean tsc as proof a type-only export exists; verify the runtime/export separately.

### Reusable technique: proving a type is enforced, not silently `any`
A clean `tsc` is also what `any` produces, so it is weak evidence. Verified with a throwaway probe file containing two `@ts-expect-error` directives on genuinely-invalid usages plus a **negative control** directive on a *valid* usage. Expected: no error for the first two, and exactly one `TS2578 Unused '@ts-expect-error' directive` for the control. The control firing is what proves the mechanism works. Probe deleted after use. Worth reusing whenever a plan's whole point is "add a type".

So the union's second member adds documentation value, not type-level strictness — `OutletBackfillPrismaClient` is effectively `Pick<PrismaClient, "outlet">`. Kept per plan.
